# Задание 6. Классификация данных

## 1. Движок классификации данных 

Для небольшой компании на этапе MVP достаточно простого отдельного контура между источниками данных и аналитическим хранилищем. Воркфлоу такой:

1. данные попадают в `Raw Landing`;
2. `Classification Engine` присваивает теги `med:*` и выявляет новые поля;
3. `Policy Decision` решает, что можно загрузить, что нужно замаскировать, а что отправить в `Quarantine`;
4. `De-identification Service` выполняет маскирование, токенизацию или псевдонимизацию;
5. данные загружаются в нужный слой хранилища.

Если появилось новое или неясное поле, набор данных не идёт дальше автоматически, а попадает в `Quarantine`.

Диаграмма C2 вынесена в отдельный файл: `task6/data-classified.puml`.

## 2. Специальные слои в хранилище

В хранилище нужны отдельные слои:

- `Raw Landing` - временное защищённое хранение исходных данных до классификации;
- `Quarantine` - данные с неясной классификацией или нарушением политик;
- `Confidential Layer` - чувствительные данные с ограниченным доступом по ABAC/RBAC;
- `Pseudonymized Layer` - основной слой для BI/ML/AI, где удалены прямые идентификаторы;
- `Public/Aggregated Marts` - агрегированные витрины без данных, позволяющих идентифицировать пациента.

Правила по тегам:

- `med:pii.*` и `med:phi.*` не должны попадать в общие витрины без де-идентификации;
- `med:auth.secret` запрещён к загрузке в аналитическое хранилище;
- `med:fin.*` разрешён только после минимизации и удаления лишних реквизитов;
- доступ к `Confidential Layer` должен логироваться и контролироваться отдельно.

## 3. Метрики эффективности классификации

| Метрика                  | Зачем нужна                                                     |
|--------------------------|-----------------------------------------------------------------|
| `Precision`              | Снижает число ложных срабатываний                               |
| `Recall`                 | Показывает, сколько чувствительных данных действительно найдено |
| `F1-score`               | Даёт общий баланс качества классификации                        |
| `Coverage`               | Показывает, какая доля данных размечается автоматически         |
| `Unknown rate`           | Показывает, сколько данных классификатор не смог распознать     |
| `Quarantine rate`        | Помогает понять, не слишком ли много ручной обработки           |
| `Schema drift rate`      | Показывает, как часто источники меняют структуру                |
| `Classification latency` | Позволяет контролировать скорость batch-пайплайна               |

## 4. Scalability

Для масштабирования системы нужно:

- делать `Ingestion Gateway`, `Classification Engine` и `De-identification Service` stateless;
- обрабатывать данные партициями по источникам и временным диапазонам;
- использовать асинхронное взаимодействие между приёмом данных и классификацией;
- хранить политики и словарь тегов отдельно от самого DWH;
